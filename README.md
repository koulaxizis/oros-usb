# orOS USB

A bootable USB image that starts straight into [orOS](https://useoros.online). MIT, free forever.

**Beta.** Releases are for testing. Known: on some PCs the very first start showed a white screen with a cursor, and a restart fixed it. The session watchdog (below) now restarts such a start by itself; System › Problem report shows each time it did.

## What is inside

- Debian 13 (trixie) live system, built with live-build, with the usual non-free firmware for Wi-Fi, graphics and sound.
- [labwc](https://labwc.github.io/), a Wayland compositor set up as a kiosk (`/etc/xdg/oros-labwc`: every window maximized without a title bar, no desktop menu or labwc keys), showing Debian's Chromium (no Google sign-in, sync, Safe Browsing or metrics, and it never offers to save passwords, addresses or cards: orOS Passwords and the orOS add-on keep those; see `config/includes.chroot/etc/chromium/policies/managed/oros.json`).
- The [orOS Portable](https://github.com/koulaxizis/oros-portable) launcher serving orOS from `http://localhost:47800/`, the same address as orOS Portable, so its Dropbox sign-in works here too.
- UEFI with Secure Boot (Debian's signed shim and GRUB) and legacy BIOS boot, with a graphical start: no text from the menu to orOS (see **Boot screen** below).
- A **System** button in orOS's top bar (the `system/extension` Chromium extension) for Wi-Fi, sound, battery, restart, shut down and installing orOS on the computer's disk. It talks to `oros-system` (`system/`), a small native messaging host that uses NetworkManager, PipeWire and systemd.

## Using it

1. Write the ISO to a stick: on Windows with [Rufus](https://rufus.ie) (set "Persistent partition size" to keep your data), elsewhere with balenaEtcher or `dd`.
2. Without Rufus persistence, run `sudo scripts/add-persistence.sh /dev/sdX` to add a `persistence` partition in the rest of the stick. Without one, orOS still runs, but forgets everything on shutdown. `sudo scripts/add-persistence.sh --encrypt /dev/sdX` keeps that data encrypted with a passphrase, asked on the boot screen at every start: [Encrypted data](ENCRYPTION.md) (EN/EL).
3. Boot from the stick. orOS opens full screen. In the computer's boot menu the stick may appear under another name: Acer computers, for example, call every non-Windows USB stick "Linpus lite". That is the computer's label, not a different system; after installing, the entry reads "orOS".

The System button (Wi-Fi icon, top right) has Wi-Fi, sound, Bluetooth, printers, battery, screen brightness (laptops), time zone, Restart and Shut down. With orOS 4.53.00 or newer the System button steps back and the same parts live in orOS's own Quick settings (the network and power symbols at the right end of the top bar, GNOME style): volume and brightness sliders, Wi-Fi and Bluetooth buttons, a System button that opens the full panel (printers, disks, time, update, install, problem report), and Restart the computer / Shut down in its power menu. The extension fills orOS's slots `#qs-sys`, `#qs-sys-pills` and `#qs-power-sys` when orOS sends the DOM event `oros-qs` (`open`), sets `data-oros-qs-sys` (orOS hides its own Network button) and reports the battery on `data-oros-sys-battery`. The **Internet** button next to it opens a normal browser window (tabs, address bar, DuckDuckGo search, the same no-Google settings) over orOS; closing it brings orOS back. It opens in the orOS window's own browser profile (`~/oros/data/profile`, or the signed-in user's), so it is the same browser: the **orOS add-on** there (koulaxizis/oros `extension/`, copied by `scripts/addon.sh` into `/opt/oros/addon` with its orOS address preset to `http://localhost:47800/`) fills Passwords logins, cards and addresses on web pages and offers to save new logins, and sites share storage with the orOS window as in any browser with orOS in a tab. Older images kept the Internet window in `~/oros/data/web`; its cookies and sign-ins start over once, and that folder can be deleted. To browse through a VPN, see [Private browsing](PRIVATE-BROWSING.md) (EN/EL).

Screen lock with a fingerprint: on a computer with a fingerprint reader that fprintd supports (installed in the image), orOS's Settings › Screen lock can turn on unlocking with an enrolled finger. The extension passes the page's `oros-bio` event (`state`, `seal`, `open`, `clear`) to `oros-system` (`system/lockbio.go`), which runs `fprintd-list` and `fprintd-verify` as the session's user and keeps a 32-byte secret per record in `~/oros/lock-bio.json` (0600); orOS keeps a token wrapped with it, so only a touch on the reader opens the lock. The page sees `data-oros-sys-bio` when the extension offers it. The same commands answer in orOS Portable and the desktop apps (Windows Hello there too).

System › **Disks** lists Downloads, the computer's own disks (Windows, another Linux) and USB sticks (FAT, exFAT, NTFS, ext4, Btrfs, XFS; partitions of 1 GiB or more, never the disk orOS runs from). **Open** mounts one under `/media/oros/<label>`: USB sticks and drives and other Linux disks writable, Windows disks (NTFS inside the computer, or any NTFS that holds Windows) read-only, because writing while Windows hibernates (Fast Startup) can damage them; a disk that refuses to open writable opens read-only. With an orOS that has **Files › This computer** it opens there, otherwise in the Internet window; **Close** unmounts it. From a terminal: `sudo /opt/oros/oros-system mount --dev /dev/sdX1 [--unmount]`, and `/opt/oros/oros-system disks` lists them as JSON.

**The same extension in orOS Portable.** The full orOS Portable edition and the orOS desktop apps load this extension too ([oros-portable](https://github.com/koulaxizis/oros-portable#system-in-quick-settings-full-edition-and-installers)); there the launcher is the native host. Its `status` says `platform: "portable"` and lists `caps` (sound, screen, power, sleep, exit, window, report, update, web, wifi, btSettings; later tor), and the extension shows only those: no kiosk keyboard, the orOS Network button stays, and the power menu has Full screen / Show in a window, Exit orOS, and Sleep, Restart and Shut down of the computer, each confirmed by a second click. `bg.js` switches the window (`chrome.windows.update`) and closes every window for Exit orOS; at a browser start it reloads an orOS window that opened before the extension had loaded. Without `caps` (this stick) nothing changes.

**Computer files.** The session sets `OROS_COMPUTER_FILES=1` and `OROS_FS_HELPER=/opt/oros/oros-system`, so the orOS launcher lets the orOS page (and only it) reach the home folder and the open disks: orOS Files shows them as **This computer**, next to the orOS disk, with copy and move both ways, the Trash (the freedesktop one: `~/.local/share/Trash`, or `.Trash-1000` on a disk) and opening and saving in orOS's apps. The API and its safeguards are described in [orOS Portable's README](https://github.com/koulaxizis/oros-portable#computer-files-oros-usb-only). The usual folders (Documents, Downloads, Pictures, Music, Videos, Desktop) are made at every start; on the stick they live on the persistence partition, so without one they are gone at shutdown. The extension sees the page's `data-oros-computer-files="1"` and then asks Files to show an opened disk with the DOM event `oros-files-open` (detail: `/disks/<label>` or `/home/Downloads`). The boot test plugs in a FAT32 stick labelled `OROSTEST`, and `oros-selftest-files.service` opens it, writes to it and to the home folder through the same API, and closes it.

Saved Wi-Fi networks and their passwords are kept in `/home/.oros-network` (NetworkManager's keyfile folder, set in `/etc/NetworkManager/conf.d/oros.conf`), so they survive a restart; the installer copies them to the computer. System › **Problem report** writes `~/Downloads/orOS-report-<date>.txt` (hardware, disks, network state, this and the previous start's system log, and the logs below) and shows it in the Internet window, from where it can be attached to a message. The system log is kept across restarts in `/home/.oros-journal` (100 MB at most). Logs for when something goes wrong: `~/oros/data/session.log` (the kiosk), `~/oros/data/profile/chrome_debug.log` (the orOS window), `~/oros/data/web.log` (the Internet window's start) and `~/oros/data/oros-system.log` (the System button), `~/oros/data/bridge.log` (orOS Bridge), `~/oros/data/install.log` and `update.log`.

**Boot screen.** From the computer's own logo to orOS no text shows. The boot menu is hidden: orOS starts after 2 seconds, and Esc (BIOS: any key) in that time shows the menu. The kernel line (`auto/config`) asks for `quiet splash plymouth.ignore-serial-consoles loglevel=3 udev.log_level=3 systemd.show_status=false vt.global_cursor_default=0` (Plymouth falls back to its text mode, every boot message on the screen, when it sees a serial console, which the CI tests use), and Plymouth shows the orOS logo with three breathing gold dots on orOS's dark background (`/usr/share/plymouth/themes/oros`, two-step), also when the computer restarts or shuts down. orOS itself runs as `oros-session.service` on tty1, started the way a display manager is (`Conflicts=plymouth-quit.service`, PAM service `oros-session` for a logind session): Plymouth leaves its last picture on the screen (`plymouth quit --retain-splash`) and labwc takes over from there, so no login prompt shows in between. tty2 keeps its autologin to the network screen. The pictures come from `scripts/boot-art.py` (Pillow; the PNGs are in the repository). The CI boot test takes a screenshot every 3 seconds in the first minute and fails if one shows the text console or none shows the boot screen.

**Session watchdog.** `oros-session` restarts orOS when its window shows no sign of life: the System extension pings `oros-system` every 10 s once the window has painted a frame, and the time lands in a file in RAM (`$XDG_RUNTIME_DIR/oros-alive-<uid>`). No ping within 60 s of a start, or none for 40 s later, stops the session and starts it again: the first time as it was, from the second time with the GPU off (`--disable-gpu`, also for the Internet window) for the rest of that boot. At most 3 restarts per boot. Each one is a `watchdog:` line in `session.log` and in the Problem report's first section. CI tests it with a fake compositor (`scripts/test-session-watchdog.sh`) and in QEMU with two starts that never ping (`WATCHDOG_TEST=2 scripts/test-boot.sh`); a normal boot test fails if the watchdog had to restart.

**Printing.** Driverless only, no vendor drivers: CUPS with cups-browsed and Avahi finds printers that support IPP Everywhere or AirPrint on the same network, and ipp-usb does the same for such printers on USB (almost every printer sold since about 2015). They show up by themselves in every print dialog (Ctrl+P in any app, or Print in orOS's apps) and in System › **Printers**, which also prints CUPS's test page. Queues are found again at every start, so nothing is stored.

**Scanning.** orOS Scan PDF scans from a scanner through orOS Bridge (0.9.0 or newer, below): `Add from scanner` next to the camera. The image has SANE with sane-airscan, so scanners and multifunction printers that scan without a driver (eSCL or WSD: almost every network or USB multifunction printer of recent years; USB ones through ipp-usb) work as they are, as do scanners with a driver in Debian's SANE backends. The user is in the `scanner` and `lp` groups, so the bridge may open them.

**Studio: plugins and the sound card.** [orOS Bridge](https://github.com/koulaxizis/oros-bridge) comes with the image and starts with orOS (`/usr/local/bin/oros-kiosk`, inside labwc), so orOS Studio can record through the sound card (PipeWire or ALSA, every input on its own track, MIDI keyboards) and use VST3 and CLAP plugins put in `~/.vst3` or `~/.clap`. It listens on `127.0.0.1` only, for orOS's own page. The first time Studio connects it asks for a pairing code: the bridge has no window here, so the code shows at the top of orOS (the System extension reads it through `oros-system`, from the file the bridge keeps in RAM, `--code-file`) and goes once it is typed. A plugin's own window opens over orOS (XWayland) and closing it brings orOS back. Log: `~/oros/data/bridge.log`, also in the Problem report.

**Bluetooth.** System › **Bluetooth** (shown when the computer has it) turns it on and off, finds devices for 10 seconds, pairs them (a keyboard shows the code to type on it), and connects, disconnects or forgets paired ones. Headphones and speakers play through PipeWire. Pairings are kept in `/home/.oros-bluetooth`, bound onto `/var/lib/bluetooth` by `oros-bluetooth.service`, and the installer copies them.

**Time.** The clock is set from the internet (systemd-timesyncd with Debian's `debian.pool.ntp.org` servers). System › **Time** picks the time zone (UTC until then); it is kept in `/home/.oros-timezone`, set again at every start by `oros-time.service`, and copied by the installer, whose screen offers the same choice. From a terminal: `sudo /opt/oros/oros-system time --zone Europe/Athens`. Computers that also run Windows keep local time in their hardware clock, so offline the clock can be off by the time zone's hours until the stick goes online. Brightness uses `brightnessctl`; each start begins at the computer's own level.

**Night Light.** orOS's Night Light (Settings › Appearance, and its button in Quick settings: a warmer screen from sunset to sunrise, at set hours or always) changes the screen's real colours here instead of tinting orOS's page, so the Internet window, Tor Browser and plugin windows turn warm too. The extension sets `data-oros-sys-night="1"` when `oros-system status` reports `night` (wlsunset is installed and the session is Wayland); orOS then sends the DOM event `oros-night` with the colour temperature in kelvin (`"0"` = normal), and `night.set` (`system/night.go`) runs one [wlsunset](https://git.sr.ht/~kennylevinsen/wlsunset) (MIT, Debian package) in the background on labwc's wlr-gamma-control, at that steady temperature (`-t K -T K+1`), replacing the previous one; `0` stops it. orOS does the schedule and the 20-minute fades itself. Without the extension or wlsunset, orOS falls back to its own filter; so it does when the compositor has no wlr-gamma-control (wlsunset quits at once: `oros-system` marks the boot in `$XDG_RUNTIME_DIR`, stops reporting `night`, and the extension removes the attribute). The boot test's desk self-test logs whether gamma works (`info night light gamma`). Log: `~/oros/data/night.log`.

**Lock screen power.** orOS's lock screen (orOS LOCKPOW-1) keeps an empty `#lock-power-sys` at its foot and sends the DOM event `oros-lock` (`open` / `close`). The extension fills it with `Sleep`, `Restart` and `Shut down` (`.lk-pow` buttons, orOS's own style): a first tap arms a button for 5 seconds ("Tap again: Restart"), a second one runs `power.sleep`, `power.reboot` or `power.off`, so a brush of the hand turns nothing off. A portable copy shows them only where its host reports the `power` (and `sleep`) capability. In a plain browser the box stays empty and hidden.

**Storage card.** `status` also answers `disk: { free, total }` (bytes, the disk that holds the home folder), and the extension writes it on orOS's page as `data-oros-sys-disk="<free> <total>"` every 30 seconds. orOS's Storage card in the top bar (orOS STORE-1) shows that disk's free space instead of the browser's own estimate, with the warning colour under 10 %.

**Keep awake.** orOS's `Keep awake` button in Quick settings sets `<html data-oros-awake="1">`. The extension sends it with the watchdog's ping (every 10 s, and at once when it changes); `oros-system` touches `oros-awake-<uid>` in `$XDG_RUNTIME_DIR` while pings say so and removes it on the first ping that does not. `oros-system idle` stops swayidle while the file is less than 45 s old, so the screen stays on and the computer does not sleep; when the hold ends, or orOS stops pinging, swayidle starts again with the saved times (`system/desk.go`, `TestAwakeHold`).

**Encrypted data (optional).** Sticks prepared with `scripts/add-persistence.sh --encrypt` or `make-combo-sticks.sh --encrypt`, and installs with **Encrypt my data with a passphrase** (`oros-system install --encrypt`), keep the data partition in a LUKS2 container (Argon2id). orOS asks for the passphrase on its boot screen, under the logo (`oros-unlock` in the initramfs, through Plymouth); Enter alone starts without the data. System updates then go to their own unencrypted `orossys` partition, which GRUB reads before the passphrase. Details, layout and limits: [Encrypted data](ENCRYPTION.md) (EN/EL).

**Private browsing.** Chromium (the orOS and Internet windows) looks up names with DNS over HTTPS (Chromium policy `DnsOverHttpsMode` `automatic` with [Quad9](https://quad9.net/)'s `https://dns.quad9.net/dns-query`, falling back to the network's DNS when it does not answer, so hotel Wi-Fi sign-in pages still open); the internet provider then no longer sees the names looked up, but still sees which servers the computer talks to. The Internet window also loads [uBlock Origin Lite](https://github.com/uBlockOrigin/uBOL-home) (GPL-3.0, Raymond Hill), the Manifest V3 version of uBlock Origin (Chromium no longer runs Manifest V2 extensions): `scripts/ubol.sh` takes the Chromium build of its latest release from GitHub at build time (checked against the SHA-256 GitHub lists for it, never through the Chrome Web Store) and unpacks it to `/opt/oros/ubol`, and `oros-session` copies it to `~/oros/ubol` (Chromium writes its indexed filter rules into an unpacked extension's folder and refuses a read-only one) and loads it with the System extension and the orOS add-on when the browser starts (one `--load-extension` list; `oros-system` passes the same list to the Internet window). Its filter lists come inside the extension, so each monthly image brings fresh ones; its icon turns it off for one site. Since the Internet window shares the orOS window's browser, it runs there too; it is not loaded in Tor Browser (Tor Project advises against extensions there). The **Tor** button next to Internet opens the official [Tor Browser](https://www.torproject.org/) over orOS; closing it brings orOS back. The image does not carry it: the first press asks, then `oros-system tor --fetch` reads torproject.org's `downloads.json`, downloads the 64-bit Linux build (about 110 MB) into `~/.local/share/oros-tor` on the persistence partition, checks its OpenPGP signature in `oros-system` itself (`system/torsig.go`, ProtonMail go-crypto, the same check as orOS Portable) against Tor Browser's signing key (fingerprint `EF6E 286D DA85 EA2A 4BA7 DE68 4E2C 6E87 9329 8290`, fetched and checked by `scripts/tor-key.sh` at build time into `/opt/oros/tor-browser-developers.gpg`; when that key cannot check a newer release, for example after the Tor Project renews its signing subkey, the key is fetched again from torproject.org or keys.openpgp.org and used only with the same fingerprint), unpacks it and starts it; the button shows the progress. Later presses start it at once, and Tor Browser updates itself. The System panel's **Remove Tor Browser** (`tor.remove`) deletes it with its bookmarks and frees about 400 MB; the button downloads it again when needed. orOS Portable and the desktop apps have the same button (oros-portable `launcher/tor.go`); there a full-screen orOS steps aside (`window.away` / `window.back` in `bg.js`) while Tor Browser's window is open. Without a persistence partition it is downloaded again after every restart (the question says so). The installed system works the same way. Log: `~/oros/data/tor.log`. CI downloads and checks the real Tor Browser with the same code on every build. A VPN extension for the Internet window: [Private browsing](PRIVATE-BROWSING.md) (EN/EL). Extensions the user adds there cannot reach orOS's own pages: the managed policy (`ExtensionSettings`) sets `runtime_blocked_hosts` `*://localhost`, `*://127.0.0.1` and `*://*.useoros.online` for every extension, and gives only the System extension (`hibkbfiidcfohidigfegiadgedhmdecc`) and the orOS add-on (`cbabbleeefcdjmjjdpfiojpmiekpmcci`, a fixed ID from the public key `scripts/addon.sh` puts in its manifest) their own entry without it. So a VPN or any other extension cannot read an unlocked orOS (Passwords, Notes) in the shared profile; a proxy still works for the whole browser. `system/policy_test.go` checks that the IDs match the keys. The add-on's new fixed ID means it starts over once after the update (a "Remember on this device" unlock is asked again).

**Local AI.** orOS's Assistant can answer with an open AI model that runs on this computer, without internet and without anything leaving it. System › **Local AI** has one button, **Install local AI**: it downloads [Ollama](https://github.com/ollama/ollama) (MIT) and the [Qwen 3.5](https://ollama.com/library/qwen3.5) model (Apache-2.0, the same family the browser Assistant offers) that suits the computer's memory: Tiny (`qwen3.5:0.8b`, about 1.3 GB) under 5 GiB, Small (`qwen3.5:2b`, about 2.7 GB) under 7 GiB, Medium (`qwen3.5:4b`, about 3.3 GB) under 14 GiB, Large (`qwen3.5:9b`, about 6.6 GB) from 14 GiB (a "16 GB" computer). A Qwen3 model installed before 2026-11 stays and can still be removed under **More choices**, but is no longer offered. **More choices** offers the other sizes, turning the graphics card off, and removing a model or everything. orOS's Assistant has the same button in its settings (the DOM event `oros-ai` with `install`, below). The image does not carry Ollama: `oros-system ai --fetch --model M` streams the official Linux archive from the GitHub release that the build pinned (`scripts/ollama.sh` writes `/opt/oros/ollama.json` with its address and the SHA-256 that both GitHub and the release's `sha256sum.txt` list), computes its SHA-256 while it unpacks into a temporary folder, and keeps the result only when it matches; it keeps the program, its processor libraries (variants from SSE4.2 to AVX-512, so old processors work) and the Vulkan library, about 115 MB of the 1.5 GB download, and skips NVIDIA's CUDA libraries, which need NVIDIA's own driver. The model comes through Ollama itself, which checks each part's digest. Everything goes to `~/.local/share/oros-ai` on the persistence partition, so it stays across restarts and system updates and the installer copies it with the home folder; without a persistence partition the button explains why it cannot install. Ollama listens on `127.0.0.1:11434` only, lets in only orOS's page (`OLLAMA_ORIGINS=http://localhost:47800`; Ollama itself also refuses other sites and other host names), never offers Ollama's cloud models (`OLLAMA_NO_CLOUD=1`), runs one answer and one model at a time, and frees the model's memory five minutes after its last answer. It uses a discrete graphics card through Vulkan with the image's Mesa drivers (AMD and Intel cards; NVIDIA only where Mesa's NVK driver supports the card, mostly newer ones), otherwise the processor; "Use the graphics card" off sets `OLLAMA_VULKAN=0`. `oros-session` starts it once per boot (`oros-system ai --serve`), outside labwc, so a watchdog restart leaves it running. Only the owner installs or removes it. The page reads its state from `data-oros-sys-ai` (`ready`, `off` or `none`), with `data-oros-sys-ai-url` and `data-oros-sys-ai-models` when ready; the DOM event `oros-ai` with `open` opens this section, `install` also asks to install, and `status` answers with `oros-ai-status`. Logs: `~/oros/data/ai.log` (the setup) and `ai-serve.log`. CI downloads the real Ollama and the smallest model (`qwen3.5:0.8b`) with the same code on every build, checks every offered model's name and size against Ollama's library (`scripts/check-catalog.sh`) and checks that orOS's page gets an answer and another site does not.

**Games (system side).** The image carries what Steam, Heroic (Epic, GOG, Amazon), itch and Lutris need from the system, so that Windows games run through Proton and Wine as well as Linux allows (wave G1, 2026-11-22; the programs themselves come later through the software center, as Flatpaks from Flathub, which bring their own 32-bit libraries): Vulkan with Mesa (AMD, Intel, and NVIDIA through NVK; NVIDIA's own driver is a later wave), [Flatpak](https://flatpak.org/) with xdg-desktop-portal and its GTK portal (`/etc/xdg-desktop-portal/portals.conf`), [gamemode](https://github.com/FeralInteractive/gamemode) (the processor at full speed while a game runs), Valve's udev rules for controllers (`steam-devices`; `uinput` is loaded so Steam Input can make virtual controllers), and the kernel settings SteamOS uses (`/etc/sysctl.d/80-oros-games.conf`: `vm.max_map_count` 2147483642, `kernel.split_lock_mitigate` 0). `oros-system idle` also owns `org.freedesktop.ScreenSaver` on the session bus (`system/games.go`): while a game, Steam, gamemode or a portal holds it, the screen does not go off and the computer does not sleep, as with orOS's Keep awake; a program that quits or crashes loses its hold. The boot test checks every part inside the session (`selftest-desk`: a Vulkan device, Flatpak, the portal, gamemode, `/dev/uinput`, the kernel setting, a hold taken and given back). Games that use kernel anti-cheat (Valorant, Fortnite and others) do not run on Linux at all.

**Graphics cards.** `oros-system gpu` lists the computer's graphics cards (from `/sys/class/drm`: vendor, model through `lspci`, the kernel driver in use, which card drives the screen) and the Vulkan devices Mesa offers; System › Problem report includes it, and the extension can ask for it with `gpu.status`. On a laptop with two cards (the screen on Intel or an AMD APU, a second AMD or NVIDIA card), every session start runs `oros-system gpu --apply`, which points all Flatpak programs (games, Steam, Heroic, Lutris, itch) at the second card in Flatpak's global override (`~/.local/share/flatpak/overrides/global`, group `[Environment]`, edited by `gpu.go` so other overrides stay; Mesa's `DRI_PRIME=pci-…`, which also picks the Vulkan device, NVK included; with NVIDIA's own driver its PRIME render offload variables), while orOS and the desktop stay on the card that drives the screen, which saves the battery. A desktop whose monitor is on the graphics card, a single card, a card no driver took or one passed to a virtual machine changes nothing. Nothing to choose; `gpu.offload` with `on: false` (owner only, kept in `~/oros/data/gpu.json`) turns it off. Tests: `system/gpu_test.go` (fake sysfs trees: Intel + NVIDIA, AMD APU + AMD card, desktop, VFIO), and the boot test checks the card QEMU shows and the override.

**NVIDIA's own driver.** Mesa's nouveau drives NVIDIA cards out of the box (with Vulkan through NVK on GeForce 16/20 and newer); for full speed, NVIDIA's own driver comes as a separate download, built for this exact system: `scripts/nvidia-pack.sh` installs Debian 13's packages (the 550 branch: GeForce 700/900/10/16/20/30/40 and newer, laptop chips included) in a throwaway copy of the system, builds the modules for its kernel with DKMS, signs them with the orOS key, and packs the driver's files under `/usr` as a [systemd-sysext](https://www.freedesktop.org/software/systemd/man/latest/systemd-sysext.html) image, `orOS-USB-<version>-nvidia.raw`, a file of each release. The image only carries its description, `/opt/oros/nvidia.json` (size, SHA-256, NVIDIA's list of the cards it supports), the orOS certificate `/opt/oros/oros-mok.der` and `nvidia-sources.txt`. On a computer with a supported card and a persistence partition, `oros-system nvidia --auto` (each session start) installs it by itself when nothing needs the person (Secure Boot off, or the orOS key already enrolled); otherwise the System panel asks (`nvidia.status`, `nvidia.install`, `nvidia.progress`, `nvidia.remove`, owner only). `oros-system nvidia --install` (root, through sudo; only the official release for this system) downloads the pack into `/home/.oros-gpu` (root's folder) and keeps it only when size and SHA-256 match, then writes `/oros-system/gpu.cfg` on the partition GRUB reads updates from: GRUB adds `${oros_gpu}` to every entry (`modprobe.blacklist=nouveau nvidia-drm.modeset=1 nvidia-drm.fbdev=1`). With Secure Boot on it also asks the firmware to enrol the orOS key (`mokutil --import` with a one-time 8-digit code that the System panel shows): at the next start a blue screen (MokManager) asks for *Enroll MOK*, *Continue*, *Yes* and the code, once per computer. At every start `oros-nvidia.service` merges the pack for this system over `/usr` and loads the modules before the session; a new system whose pack is not there yet, a missing key, an unsupported card or any failure unmerges it and loads nouveau, so the screen always comes up. `oros-system update` downloads the new system's pack too when a driver is installed (`update.json` `nvidia`), and keeps the packs the boot menu's systems use. Kepler cards (GeForce 600/700 that need NVIDIA's 470 branch, which Debian 13 no longer builds) stay on nouveau; BIOS starts (isolinux cannot read `gpu.cfg`) too. On a laptop with two cards `gpu.go` then sets NVIDIA's PRIME offload variables for games. The CI boot test merges the build's pack in QEMU and checks its files and that its modules are signed for the running kernel (`oros-selftest-nvidia.service`). The release signing key is the repository secret pair `NVIDIA_MOK_KEY` / `NVIDIA_MOK_CERT` (PEM); without it a build makes a key of its own (`"ephemeral": true` in `nvidia.json`), which works with Secure Boot off.

**Software center.** Settings › Software offers only software that was tried on orOS (wave G3, 2026-11-22), from the catalog the image carries (`catalog/catalog.json`, copied to `/opt/oros/catalog.json`): orOS's own first (local AI, Claude desktop, Tor Browser, NVIDIA's driver, which keep their own buttons and commands), then game stores and tools from [Flathub](https://flathub.org) (Steam, Heroic, itch, Lutris, Bottles, ProtonPlus), add-ons for the Internet window (Proton VPN, Windscribe, Privacy Badger) and more open models for the local AI (IBM Granite, Microsoft Phi-4 mini, Mistral, Ai2 OLMo 2, DeepSeek-R1; Apache-2.0 or MIT). `oros-system soft` (`system/soft.go`, as the person) installs a Flathub app into the home folder (`flatpak --user`, so it stays on the persistence partition), removes it with the runtimes nothing else uses, updates every app, and once a day at the session start updates them by itself (`soft --auto`). Flathub is added from the `flathub.flatpakrepo` the build fetched, with a filter the build wrote from the same catalog (`/opt/oros/flathub.filter`: `deny app/*` and one `allow` per app; runtimes, Proton and the graphics drivers for Flatpak stay allowed), so nothing else can come from it; each start sets the filter again, so a new system's catalog applies at once. Add-ons are one click too: the owner's choice is kept in `~/oros/data/addons.json`, and root's `oros-system addons --apply` (one sudo rule, no arguments; each session start and each change) writes Chromium's `ExtensionInstallForcelist` policy (`/etc/chromium/policies/managed/oros-addons.json`) with the ones the catalog lists; Chromium then installs them from the Chrome Web Store, checks them and keeps them up to date, and taking one away removes it. `oros.json` still keeps every add-on off orOS's own pages. The extension's commands: `soft.list` (catalog, what is installed, progress, free space), `soft.install`, `soft.remove`, `soft.update`, `soft.addon` (owner only), `soft.open` (the app opens maximized; orOS takes the whole screen back when it closes). The catalog's models appear in the local AI's choices (`ai.status` `offer`). CI checks the catalog against the real sources on every build (`scripts/check-catalog.sh`: each app on Flathub, each add-on on the Chrome Web Store as a Manifest V3 extension, each model in Ollama's library at about its size), and the boot test adds Flathub with the image's filter in a throwaway folder and checks that it shows exactly the catalog's apps. The System panel shows it as **Software** (one button per program: Install, then Open; add-ons as switches; updating and removing under More choices; the DOM event `oros-soft` with `open` opens it) and, above it, **Graphics card** (the cards, the switch for games on a laptop's strong card, and NVIDIA's driver: one button, then with Secure Boot on the 8-digit code for the blue screen and Restart now; an old Kepler card says why it stays on nouveau). Tests: `system/soft_test.go`.

**Game library on another disk.** Games take tens of gigabytes, more than a stick's persistence partition holds. Settings › Software › *Game library on another disk* lists the disks that can hold one (ext4, ext3, btrfs or xfs, 16 GB or more; FAT, exFAT and NTFS cannot keep Proton's Windows folders working) and, on the owner's click, root (`oros-system mount --games-set DEV`, the Disks sudo rule) opens it at `/media/oros/games`, writable and with programs allowed to run (other disks open `noexec`), adds a `Games` folder owned by the person and remembers the disk by its UUID in `/home/.oros-games.json`. Each session start opens it again when it is plugged in (`mount --games-boot`), and a Flatpak override lets the center's game stores write there (`--filesystem=/media/oros/games`). In Steam it is added once under Settings › Storage › Add drive; in Heroic and Lutris it is the install folder. `games.disk` and `games.diskSet` (owner only; an empty disk stops it, nothing on the disk is touched). Tests: `system/gamesdisk_test.go`.

**Console mode.** Settings › Software › *Console mode* (shown once Steam is installed) turns the computer into a games console for the television and a controller: `console.start` writes the request file (`$OROS_CONSOLE`) and ends labwc, and `oros-session` runs `oros-system console --run` on tty1 in its place: Steam's Big Picture (`flatpak run com.valvesoftware.Steam -gamepadui`) as the only window of labwc's kiosk set-up. Debian 13 has no gamescope package; when a later image carries one, gamescope (`-e`, Steam steers the frame limit and scaling) is used first, and labwc again when it fails within 20 s (some old cards, virtual machines). Power › Exit Steam ends it and orOS starts again. The owner can make every start of the computer begin in console mode (`console.boot`, `~/oros/data/console.json`; only the first start of a boot, so leaving Steam always reaches orOS). The boot test notes which of the two it would use. Tests: `system/console_test.go`.

**Claude beside orOS.** The session runs [labwc](https://labwc.github.io/) instead of cage since 2026-11-16 (Chris: «Claude δίπλα στο orOS»), so two windows can share the screen. When the person opens Claude desktop from orOS (System › Claude desktop or Settings › Connected services › Claude), labwc's window rules (`/etc/xdg/oros-labwc/rc.xml`) snap Claude to the right half and the orOS window (a Chromium window titled `orOS…`) to the left; with their own Claude account and orOS Gate, Claude sees what they allow without a window switch. When Claude closes, the small shell `startClaude` runs it in calls `wlrctl toplevel maximize title:orOS`, so orOS has the whole screen again. Every other window (the Internet window, Tor Browser, a plugin's window) opens maximized as under cage.

**orOS Gate behind the screen lock (opt-in).** orOS's window never closes on orOS USB, so the orOS Portable launcher the session runs (`OROS_COMPUTER_FILES=1`) offers only the lock rule of oros-portable `launcher/gatehost.go` (oros Bible "GATE-HOST"): with Settings › orOS Gate › `Keep the Gate working behind the screen lock` on (off by default), the window opens at `/?gate-host=<nonce>` and, once the launcher confirms that nonce, Claude's changes are made at once even while the screen is locked. Dialogs, apps Claude opens and deletions that ask the person wait for an unlock, and Sensitive work turns it off. No background browser runs on a stick; nothing in this repository changes for it.

**Screens, power, keyboard, screen reader** (`system/desk.go`, `system/display.go`; choices in `~/oros/data/desk.json`, every value checked when read). System › **Screens**: with a second screen, *Extend* places the screens side by side (the built-in one first) and orOS spans them, so multitasking's side by side puts one app on each; *Duplicate* puts them on top of each other at a resolution they share, or scales the others to the first one's size; *Only the other screen* and *Only this screen* turn the rest off (with the lid shut and a screen plugged in, logind does not suspend). Each screen keeps its resolution and size (100 to 200%). It goes through `wlr-randr` (labwc's wlr-output-management) and is applied again when a screen is plugged in or out. System › **Power**: the screen goes off after 10 minutes without use (2 to 30, or never) and the computer can sleep after 15 minutes to 2 hours (never by default): `oros-system idle` runs `swayidle` inside labwc with those times and starts it again when they change; `oros-system screen --off` uses `wlopm` (wlr-output-power-management) where the compositor has it; where it does not (Debian 13's labwc did not; the boot test records what labwc does), a laptop's backlight goes to 0 and orOS is covered with black until the next key or move (a desktop monitor's own light stays on; only the picture goes). A playing video keeps the screen on (Chromium's idle inhibitor). Sleep is in the panel and the power menu (`power.sleep`, polkit allows `login1.suspend`); closing the lid suspends as before. orOS's screen lock locks after the wake when its idle time has passed (it counts with the clock). System › **Keyboard**: up to four layouts (31 offered, German among them) and the switch combination (Alt+Shift, Super+Space, Ctrl+Shift or Caps Lock); `oros-session` reads them with `oros-system keyboard --layouts|--options` before every start of labwc, which reads `XKB_DEFAULT_*` only when it starts, so **Apply** starts orOS again (orOS keeps its data). System › **Accessibility**: the [Orca](https://orca.gnome.org/) screen reader with [eSpeak NG](https://github.com/espeak-ng/espeak-ng) voices through speech-dispatcher, all on the computer (no online voices). Turning it on starts orOS again once, because Chromium shows the page to a screen reader only when it starts with `--force-renderer-accessibility` (`oros-session` adds it while the reader is on); `oros-kiosk` then starts Orca with the language orOS had (English, Greek or German locales are generated for Orca alone). Chromium starts with `--enable-speech-dispatcher`, so orOS's own read-aloud gets the same local voices. **Screenshots**: PrtSc (or Ctrl+Alt+Shift+G) saves the whole screen with `grim` (labwc's screencopy) as `Pictures/Screenshots/Screenshot <date> <time>.png` in the signed-in user's home and offers to open it in Files. The keys are orOS's Ctrl+Alt+Shift shortcuts; orOS lists them as orOS USB's own and keeps the current key on `<html data-oros-sc-usb-shot|usb-reader|usb-display>` (an empty value turns one off). The boot test checks a screenshot, the screens, swayidle, the keyboard labwc runs with, the espeak-ng voices and Orca from inside the session (`oros-system selftest-desk`).

**Claude desktop.** System › **Claude desktop** (and orOS's Settings › Connected services › Claude, through the DOM event `oros-claude`) installs Anthropic's [Claude desktop](https://claude.com/download) app, which opens over orOS like Tor Browser; closing it brings orOS back. The image does not carry it (it is Anthropic's proprietary app, not ours to pass on): after a question, `oros-system claude --fetch` reads Anthropic's apt repository the way apt does: `dists/stable/InRelease`, whose OpenPGP signature is checked in `oros-system` (ProtonMail go-crypto) against the repository key pinned by fingerprint `31DD DE24 DDFA B679 F42D 7BD2 BAA9 29FF 1A7E CACE` (as Anthropic's [Linux install guide](https://code.claude.com/docs/en/desktop-linux) publishes it; `scripts/claude-key.sh` fetches it at build time into `/opt/oros/claude-desktop.gpg`, and a renewed key is fetched again from `downloads.claude.ai` and used only with the same fingerprint), then the `Packages` index and the newest `claude-desktop` `.deb` for this processor (amd64 or arm64), each kept only when its size and SHA-256 match the signed list. The package is unpacked with `dpkg-deb -x` into `~/.local/share/oros-claude` on the persistence partition (the system itself starts fresh at every boot and with every system update, so apt cannot keep it), its program is found through `/usr/bin/claude-desktop` (links followed inside the package only), and `ldd` must find every library it needs on this system, else nothing is kept and the reason is shown. Each user of the stick has a copy of their own and signs in with their own Claude account; `Check for a newer version` repeats the steps and downloads only a newer version; `Remove Claude desktop` deletes the program and keeps the sign-in (`~/.config/Claude`). Without a persistence partition it is not offered. orOS's page reads `data-oros-sys-claude` (`none`, `busy`, `ready`, `cannot`) and `data-oros-sys-claude-why` (`persist`, `os`, `net`, `fail`) and sends `oros-claude` with `install` (the extension asks first), `open`, `remove` or `status`. Logs: `~/oros/data/claude.log` and `claude-run.log`. CI downloads and checks Anthropic's real package with the same code on every build.

`~/oros/app` links to the orOS in the image; `/opt/oros/oros-portable update` replaces it with a newer copy on the persistence partition, and a newer image resets it.

### Several users on one stick

orOS Settings › Users adds people to the stick (the orOS Portable launcher's users, see its README). From then on orOS starts with a sign-in window (names, password or PIN, an optional guest; Restart and Shut down at the top right) and each user gets their own orOS: their own data, sync account, Internet window profile and, in Files › This computer, a home of their own (`~/oros/homes/<id>`; the first user keeps `/home/oros`). Signing out in orOS closes the user's windows and brings the sign-in window back. Only the owner sees System update and "Install orOS on this computer" (`oros-system` refuses them for the others). With the stick encrypted (see ENCRYPTION.md) the passphrase at boot protects everybody's data; the sign-in passwords keep users apart on the screen. On top of that each user other than the first may encrypt their own files with their own password (Settings › Users › Encrypt my files; [Encrypted data](ENCRYPTION.md#each-users-own-files)): nobody else, the owner included, can open them, on this computer or another.

### System updates

A new orOS USB is built and released every month (newer Chromium, kernel and firmware from Debian 13, and the latest orOS), after the same tests as every build. System › **System update** downloads its system (about 1.2 GB) onto the persistence partition, into slot A or B, whichever is not running, checks it against `update.json`, and writes `/oros-system/boot.cfg`. On the next start the boot menu (UEFI) starts the new system; the previous one and the stick's own system stay in the menu as a way back. Files and settings stay, because the persistence partition only keeps the home folder. Old BIOS computers keep starting the stick's own system. From a terminal: `sudo /opt/oros/oros-system update --yes`.

### Installing on the computer

System button → **Install orOS on this computer** erases the chosen internal disk and puts orOS on it: a FAT partition with the boot files and the system image (UEFI with Secure Boot), and an ext4 partition labelled `orosdisk` that keeps the home folder, optionally copied from the stick, and optionally encrypted with a passphrase ([Encrypted data](ENCRYPTION.md); disks of 16 GB or more). The installed system starts like the stick, without it, and no longer offers to install. From a terminal: `sudo /opt/oros/oros-system install --disk /dev/sdX --yes`. UEFI only; old BIOS-only computers keep using the stick.

### Combo sticks (orOS USB + orOS Portable)

`sudo scripts/make-combo-sticks.sh [--encrypt] ISO orOS-Portable-<version>.zip /dev/sdX [/dev/sdY ...]` writes sticks that do both: they boot orOS on any PC, and in Windows or Linux they show an NTFS drive `OROS` with [orOS Portable](https://github.com/koulaxizis/oros-portable), which runs without a restart. Layout: the image, then the NTFS partition, then the `persistence` partition (half of the free space by default, or `--persistence-gib N`). Each stick is read back and checked: the image byte for byte, the Portable files against `SHA256SUMS.txt`. 32 GB sticks or larger. The two modes keep separate data.

## Building

`sudo scripts/build.sh <version>` on Debian 13, or let CI do it: `.github/workflows/build.yml` builds the ISO in a privileged `debian:trixie` container, writes it to a disk image with a persistence partition, boots it in QEMU with UEFI Secure Boot (Microsoft keys), and checks that orOS started, the System button reached `oros-system`, and orOS saved its profile to the persistence partition. It then installs orOS from the ISO onto an empty disk image with `oros-system install` and boots that disk alone the same way (`scripts/test-install.sh`), repeats the update and install tests with encrypted data (a test passphrase typed on the boot screen, a wrong one first), and writes a combo stick image with the orOS Portable lite release and boots it (`scripts/test-combo-sticks.sh`), and puts the image's system onto a stick's persistence partition with `oros-system update` and boots it (`scripts/test-update.sh`). Tags, manual runs with a tag, and the monthly run (1st of the month) publish a release with the ISO and the update files. Screenshots of the boot are kept as the `boot-test` artifact. `v*` tags publish a release.
